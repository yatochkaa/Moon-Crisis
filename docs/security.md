# Безопасность

## Threat model (без «security theatre»)

Контекст: локальный тестовый проект без аутентификации и без публикации в интернет.

| Угроза | Статус | Мера |
| --- | --- | --- |
| Клиент присылает выгодные ему числа (награда, риск, результат) | закрыто | в API принимаются только `orderId`, `roverId`, `idempotencyKey`; Zod-схемы `strict()` отклоняют лишние поля; всё остальное сервер считает из базы |
| Двойной клик / повторная отправка → двойная награда | закрыто | `idempotencyKey` + unique-индекс в БД + проверка внутри транзакции + `disabled` на кнопке |
| Гонка: два запуска одного ровера | частично | всё в одной транзакции с перезагрузкой строк; SQLite сериализует запись, но может вернуть ошибку блокировки (см. ниже) |
| Утечка внутренних деталей (stack trace, текст Prisma, SQL) | закрыто | `toErrorResponse` превращает любое неизвестное исключение в `INTERNAL_ERROR`; детали логируются только на сервере |
| Prisma Client в client bundle | закрыто | `import 'server-only'` в `infrastructure/prisma.ts`, ESLint-правило `no-restricted-imports` для `@prisma/client` |
| XSS через тексты заказов/событий | закрыто | только текстовые узлы React, `dangerouslySetInnerHTML` не используется; CSP в `next.config.ts` |
| SQL-инъекции | закрыто | только типизированные вызовы Prisma, raw SQL не используется |
| Секреты в репозитории | закрыто | секретов нет; есть `.env.example`; `.env`, `*.db` и артефакты в `.gitignore` |
| Некорректные данные в базе (ручная правка SQLite) | снижено | все строки проверяются Zod-схемами в `infrastructure/mappers.ts` |
| **Отсутствие аутентификации** | **открыто осознанно** | любой, кто имеет доступ к порту, управляет единственной игровой сессией. Для локального тестового задания это допустимо; в production нужны аутентификация и привязка сессий к пользователю |
| Нет rate limiting | открыто осознанно | локальный проект без внешнего доступа; в production — лимиты на мутации |
| CSRF | открыто осознанно | нет cookie-аутентификации → классический CSRF не применим; после ввода аутентификации потребуется защита |

## Доверенные и недоверенные данные

Недоверенные (валидируются всегда):

- тело HTTP-запроса (`orderId`, `roverId`, `idempotencyKey`);
- строки из SQLite (enum-поля — просто TEXT);
- переменные окружения (`ALLOW_GAME_RESET` сравнивается со строгим `'true'`).

Доверенные: только результаты собственных чистых функций над уже проверенными данными.

Клиент никогда не передаёт: `reward`, `batteryCost`, `risk`, `result`, `credits`, `battery`, статусы. Они вычисляются заново внутри транзакции. Preview — только информация для UI и не влияет на результат.

## Защита от повторных запросов

1. Клиент генерирует `idempotencyKey` (`crypto.randomUUID()`) один раз на попытку и повторно использует его при retry.
2. Кнопка запуска блокируется (`disabled`) на время запроса.
3. На сервере внутри транзакции сначала ищется Delivery с таким ключом: если найдена — возвращается сохранённый результат с `replayed: true`, `creditsAwarded: 0` и HTTP 200. Новой доставки и повторного начисления не происходит.
4. На уровне базы `Delivery.idempotencyKey` — UNIQUE. Даже если два запроса пройдут проверку одновременно, вторая вставка упадёт и транзакция откатится — база является последней линией защиты, а не единственной.

## Транзакционность

`startDelivery` выполняет всё внутри `uow.transaction` (реализация — `prisma.$transaction`):

1. перезагрузка сессии, заказа, ровера, локации;
2. проверка актуальных статусов; 3. проверка `idempotencyKey`; 4. пересчёт preview; 5. проверка ограничений; 6. результат по `roll`; 7. создание Delivery; 8. списание батареи; 9. статус заказа; 10. награда только при успехе; 11. рейтинг; 12. GameEvent; 13. проверка победы/поражения; 14. безопасный DTO.

Любое исключение отменяет все записи: частичных состояний («батарея списана, награда не начислена») быть не может. Откат проверяется интеграционным тестом.

`endDay` и `resetGame` также выполняются в транзакции.

## Секреты и конфигурация

- Секретов в проекте нет. Единственные переменные — `DATABASE_URL` и `ALLOW_GAME_RESET`.
- В репозитории только `.env.example`; `.env`, `.env.local`, `*.db`, `*.db-journal` игнорируются.
- Переменные без префикса `NEXT_PUBLIC_` не попадают в клиент; таких переменных в проекте нет вовсе.

## Security headers

Заданы в `next.config.ts` (`headers()`): `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, `Permissions-Policy` (камера/микрофон/геолокация выключены), `X-DNS-Prefetch-Control`. `poweredByHeader: false`.

Известное ограничение: CSP содержит `'unsafe-inline'` для стилей (и в dev — для скриптов), так как Next.js вставляет inline-стили. Корректное решение — nonce через middleware; задача записана в `TASKS.md`. `Strict-Transport-Security` не выставляется: локально HTTP, в production его нужно включить.

## Случайность

- Генерация только на сервере (`src/infrastructure/random.ts`, `node:crypto.randomInt`).
- Источник централизован и спрятан за портом `RandomSource`, поэтому легко подменяется в тестах.
- `Math.random` не используется в domain-функциях; `resolveDeliveryResult` принимает `roll` числом и валидирует диапазон `[0, 1)`.
- Криптостойкость игре не требуется, но использование `node:crypto` ничего не усложняет и исключает предсказуемость генератора.

## Ограничения SQLite и переход на PostgreSQL

Сегодня:

- SQLite допускает только одну пишущую транзакцию одновременно. При параллельных запусках второй запрос может получить `SQLITE_BUSY`; клиент увидит `INTERNAL_ERROR`, а данные останутся целыми (транзакция откатится).
- Нет `SELECT ... FOR UPDATE`: блокировка на уровне строки невозможна; защитой служат сериализация записи, перезагрузка строк внутри транзакции и unique-ограничение.
- Нет нативных enum и `Json`-типа: enum-ы — TEXT с проверкой в коде, `metadata` хранится строкой JSON и разбирается через Zod.
- База — локальный файл: нет сетевых прав доступа, защита — только файловые права ОС.

При переходе на PostgreSQL изменилось бы:

1. `datasource db { provider = "postgresql" }` + новые миграции; TEXT-поля можно заменить на нативные `enum`, а `metadata` — на `Json`. Guard-функции остались бы полезными для границы типов.
2. Появилась бы возможность явного уровня изоляции: `prisma.$transaction(fn, { isolationLevel: 'Serializable' })` или `RepeatableRead` с retry на ошибку сериализации.
3. Можно было бы блокировать строки ровера и заказа (`SELECT ... FOR UPDATE`) или добавить оптимистичную блокировку (колонка `version`, `updateMany` с условием и проверкой `count === 1`).
4. Стали бы актуальны пул соединений, таймауты, сетевой доступ и учётные данные в секрет-менеджере, TLS до базы.
5. Архитектурно изменился бы только слой `src/infrastructure`: domain и application остаются как есть, потому что зависят только от портов.

## Аудит зависимостей (`pnpm audit`)

Выполнен 13.08.2026 на закреплённых версиях. Итог: **41 уязвимость — 2 critical, 20 high, 17 moderate, 2 low**. Все найденные проблемы — в зависимостях, не в коде проекта.

| Пакет | Сейчас | Худшая severity | Патч | Статус |
| --- | --- | --- | --- | --- |
| `next` | 15.4.6 | critical (RCE в React flight protocol, GHSA-9qr9-h5gf-34mp) | >= 15.5.21 | подлежит обновлению внутри 15.x |
| `vitest` | 3.2.4 | critical (Vitest UI server, GHSA-5xrq-8626-4rwp) | >= 3.2.6 | dev-зависимость; UI не используется, обновление тривиальное |
| `@playwright/test` | 1.54.2 | high (загрузка браузеров без проверки SSL) | >= 1.55.1 | dev-зависимость |
| `postcss` | 8.5.6 | high (чтение файлов через sourceMappingURL) | >= 8.5.23 | только build-time |
| `sharp` | транзитивно из `next` | high (libvips CVE) | >= 0.35.0 | `next/image` в проекте не используется |
| `effect` | транзитивно из `prisma > @prisma/config` | high (AsyncLocalStorage под RPC) | >= 3.20.0 | только CLI Prisma, не runtime |

План реакции (без мажорных переходов, ломающих совместимость):

```bash
pnpm add next@15.5.21
pnpm add -D eslint-config-next@15.5.21 vitest@3.2.6 @playwright/test@1.55.1 postcss@8.5.23
pnpm lint && pnpm typecheck && pnpm test && pnpm build
```

Обновление `next` внутри мажора 15 закрывает оба critical/high-кластера по Next.js и подтягивает исправленный `sharp`. Уязвимость `effect` тянется из CLI Prisma 6.13 и без перехода на Prisma 7 (мажор, breaking changes) не устраняется; на runtime игры она не влияет, поэтому зафиксирована в `TASKS.md`.

Правило реагирования: уязвимости в dev-зависимостях без влияния на runtime фиксируются в `TASKS.md`; принудительное обновление мажорных версий только ради зелёного audit не делается.

## Что изменилось бы в production

1. Аутентификация и привязка `GameSession` к пользователю; проверка владения ресурсом на каждом запросе.
2. Удаление или жёсткая защита `POST /api/game/reset` (сейчас — только флаг `ALLOW_GAME_RESET`, без ролей).
3. Rate limiting и антиабюз на мутациях, аудит-лог действий.
4. PostgreSQL с явным уровнем изоляции и retry-политикой.
5. CSP без `'unsafe-inline'` (nonce), HSTS, HTTPS.
6. Структурное логирование ошибок без персональных данных вместо `console.error`.
7. Регулярный `pnpm audit` в CI и обновление зависимостей по расписанию.
