## О проекте

**Moon Courier Crisis** — это не форма заказа еды, а компактная стратегия про доставку пайков и грузов между лунной базой и опасными зонами карты. Игроку нужно пережить 12 игровых дней, сохранить рейтинг базы не ниже минимального значения и заработать как можно больше `earnedCredits`. Достижение `targetCredits` не завершает кампанию досрочно: итоговый ранг определяется заработанными кредитами после завершения кампании.

Игровой цикл простой:

1. Посмотреть карту Луны и активные точки заказов.
2. Выбрать заказ с весом, наградой, срочностью и риском.
3. Назначить подходящий ровер с нужной батареей и грузоподъёмностью.
4. При необходимости зарядить ровер или купить улучшение в инженерном отсеке, доступном со 2-го дня.
5. Запустить доставку: сервер проверяет возможность рейса, списывает батарею и переводит доставку в состояние `in_transit`.
6. После завершения серверного окна получить результат — успех или провал — и обновить рейтинг, кредиты и статусы.
7. Завершить день и получить последствия по дедлайнам, рейтингу и ночной подзарядке.

## Быстрый запуск

### Требования

- Node.js 22.12.0 или новее.
- pnpm 10 или новее. Рекомендуется pnpm 10.13.1.
- Интернет для первой установки зависимостей.

### Установка

```bash
git clone https://github.com/yatochkaa/Moon-Crisis.git
cd Moon-Crisis
pnpm install
```

Создайте `.env` из `.env.example`.

macOS/Linux:

```bash
cp .env.example .env
```

Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

Пример локального `.env`:

```env
DATABASE_URL="file:./dev.db"
ALLOW_GAME_RESET="false"
```

### Подготовка базы

```bash
pnpm db:setup
```

Команда выполняет генерацию Prisma Client, применяет миграции и запускает seed с начальными данными.

### Запуск игры

```bash
pnpm dev
```

Откройте в браузере:

```text
http://localhost:3000
```

Для локальной отладки можно включить сброс игровой сессии.

macOS/Linux:

```bash
ALLOW_GAME_RESET=true pnpm dev
```

Windows PowerShell:

```powershell
$env:ALLOW_GAME_RESET='true'
pnpm dev
```

## Игровая логика

### Основные параметры

| Сущность | Важные поля | Зачем нужны |
| --- | --- | --- |
| Заказ | вес, награда, дедлайн, базовый риск, локация | Определяет ценность и сложность доставки. |
| Ровер | батарея, грузоподъёмность, скорость, эффективность, статус | Ограничивает доступные маршруты и влияет на расход. |
| Локация | расстояние, зона риска, модификатор скорости, модификатор батареи | Делает разные участки карты неравными. |
| Доставка | заказ, ровер, итоговый риск, расход батареи, результат | Фиксирует попытку доставки. |
| Событие | тип, день, текст, метаданные | Заполняет журнал активности игрока. |

### Формулы

```text
stats              = computeRoverStats(rover)

baseDistanceCost   = distance * location.batteryModifier
cargoCost          = order.weight * 0.25
challengeHazard    = order.isChallenge && location.zoneType == "dark" ? 3 : 1
batteryCost        = ceil(((baseDistanceCost + cargoCost) / stats.efficiency) * challengeHazard)

duration           = ceil(distance / (rover.speed * location.speedModifier))

loadRatio          = order.weight / stats.capacity
risk               = clamp(round(
                       order.baseRisk
                       + location.riskBonus
                       + loadRatio * 10
                       - stats.safetyRiskReduction
                     ), 0, 90)
```

Окно ожидания результата полного рейса туда-обратно рассчитывается отдельно:

```text
baseSeconds        = clamp(ceil(duration * 4), 8, 40)
simulationSeconds  = clamp(ceil(baseSeconds * 0.8^speedLevel), 8, 40)
completesAt        = startedAt + simulationSeconds seconds
```

### Как вес влияет на доставку

Тяжёлый груз влияет сразу на две вещи:

- увеличивает расход батареи через `cargoCost`;
- повышает риск маршрута через `loadRatio`.

Поэтому лёгкий заказ может быть безопасным для быстрого ровера, а тяжёлый груз потребует грузовой модели с большей грузоподъёмностью и запасом батареи.

### Когда доставка невозможна

Запуск блокируется, если:

- заказ уже выполнен, провален или просрочен;
- ровер не найден или сейчас не `idle`;
- вес заказа больше эффективной грузоподъёмности ровера;
- расчётный расход батареи выше текущего заряда или эффективной ёмкости;
- дедлайн заказа уже прошёл;
- игровая сессия завершена победой или поражением.

В демо есть как минимум два понятных невозможных сценария: постоянный заказ-перегруз и энергетический challenge в тёмной зоне.

Обычные заказы могут переноситься между днями до своего дедлайна. Срочность вычисляется по оставшемуся сроку: `critical` — дедлайн сегодня, `urgent` — остался один день, `normal` — более длительный срок. Одновременно поддерживается не более пяти активных обычных заказов; challenge-контракты в этот лимит не входят.

### Завершение дня

За день можно запустить не более трёх операций. Завершить день при меньшем количестве операций можно только с явным подтверждением; в этом случае рейтинг уменьшается на 10. День нельзя закрыть, пока существует доставка `in_transit`. Ночью idle- и charging-роверы восстанавливают 50% эффективной ёмкости батареи, а на следующем дне генерируются новые заказы в пределах лимита активных обычных заказов.


Запуск и завершение доставки разделены. При старте сервер списывает рассчитанный расход батареи, создаёт доставку со статусом `in_transit`, фиксирует `startedAt` и `completesAt`, а ровер и заказ переводит в занятые состояния. До наступления `completesAt` завершение отклоняется. После этого сервер один раз определяет исход, начисляет награду только при успехе и возвращает ровер в состояние `idle`. Повторный запрос возвращает сохранённый результат и не начисляет награду повторно.

После завершения сервер обновляет состояние игры:

- у ровера сохраняется уменьшенный заряд;
- заказ получает новый статус;
- успешная доставка добавляет кредиты;
- неудачная доставка может ухудшить рейтинг;
- в журнал событий добавляется запись;
- доставка сохраняется в базе с рассчитанными числами.

Клиент не присылает награду, риск, расход батареи или исход — важные значения пересчитываются и проверяются сервером.

## Данные и хранение

Проект использует **SQLite** через **Prisma ORM**. Путь к базе задаётся переменной `DATABASE_URL`.

Основные модели:

```text
GameSession   # день, баланс, заработок, рейтинг, состояние победы/поражения
Location      # точки карты, расстояние, риск, скорость, расход батареи
Rover         # заряд, ёмкость, грузоподъёмность, скорость, эффективность, статус, уровни улучшений
Order         # вес, награда, срочность, риск, дедлайн, challenge-флаг, статус, локация
Delivery      # история и текущие рейсы, рассчитанные значения, время старта и завершения, результат
GameEvent     # журнал событий для интерфейса
```

`targetCredits` хранится как параметр кампании, но в текущей версии достижение этого значения не завершает игру досрочно. Итоговый ранг определяется `earnedCredits` после завершения кампании.

Открыть базу в визуальном интерфейсе Prisma:

```bash
pnpm prisma studio
```

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/game` | Получить состояние игры: сессия, карта, заказы, роверы, события. |
| `POST` | `/api/deliveries/preview` | Предварительно рассчитать доставку для выбранного заказа и ровера. |
| `POST` | `/api/deliveries` | Запустить доставку, списать батарею и создать рейс `in_transit`. |
| `POST` | `/api/deliveries/complete` | Завершить готовую доставку и один раз определить её результат. |
| `POST` | `/api/rovers/charge` | Купить зарядку ровера за кредиты. |
| `POST` | `/api/rovers/upgrade` | Купить одно улучшение ровера в доступный день. |
| `POST` | `/api/game/end-day` | Завершить игровой день. |
| `POST` | `/api/game/reset` | Сбросить локальную игру, если включён `ALLOW_GAME_RESET=true`. |

Пример ошибки:

```json
{
  "error": {
    "code": "INSUFFICIENT_CHARGE",
    "message": "Недостаточно заряда для этого маршрута",
    "details": {}
  }
}
```

## Безопасность и честность логики

- Все входные данные валидируются Zod-схемами.
- Клиент передаёт только разрешённые идентификаторы, режимы операций и ключи идемпотентности; награды, цены, риск, расход батареи и исход не принимаются от клиента.
- Расход батареи и риск пересчитываются сервером при старте, а случайный результат определяется сервером при завершении доставки после наступления `completesAt`. Клиент не может передать награду, риск, расход или исход.
- Запуск доставки выполняется внутри транзакции.
- `idempotencyKey` защищает от двойного начисления награды.
- Батарея не может уйти ниже нуля.
- Риск ограничен диапазоном `0–90`.
- Reset-эндпоинт выключен по умолчанию и предназначен только для локального тестирования.
